## 原因与修改范围

1. 报告原先在锁之前读主评估，部分路径先读模块再分配版本；评估保存/疗程阶段写入不共享源事务顺序。旧RR快照在取得锁后仍可能过时，前批已用MySQL证明，不能因版本不重复就宣称来源一致。
2. 新增 `RehabClinicalSources`：业务事务内以患者首锁协调，使用显式tenant/未删除条件的锁定当前读取得患者、疗程、评估、模块、活动疗程/计划及引用。主服务授权在回放/写入前，源变更不复用旧DO；不改全局隔离、不直接写其他系统数据库。
3. 评估保存/归档/删除、附件上传、模块upsert及初始化、报告生成，患者编辑/删除，疗程和计划关键写入口按相同聚合边界协调；活动状态与引用检查不再依赖先前的空快照。关联报告或训练计划的评估不能删除。
4. 核对发现疗程更新曾可换患者，计划更新曾可换患者/疗程或缺少新来源评估归属验证。补结构归属拒绝，已有历史不能搬家；合法相同归属操作保留。没有更改临床评分、疼痛/依从性阈值或审批权限。
5. 报告追加 `sourceSnapshot`，覆盖实际持久化的患者/疗程/评估/原始模块等输入，带协议、编码规范和SHA-256。规范化保持日期与高精度数值，可从存储JSON检验修改；生成时间、报告号不混入源摘要。同请求回放原结果，新的明确请求生成新版本，不覆盖旧JSON。

## 服务层闭环验证边界

`RehabCoreBusinessFlowTest` 直接运行真实业务Service、MyBatis-Plus CRUD、tenant拦截器及事务代理，临时H2表根据实际映射字段生成；不是仅在Mockito中拼返回值。但它不等于MySQL迁移或HTTP/浏览器验收。

- 模拟机构管理员601建档；模拟治疗师501处理自己患者，非关联999拒绝。角色、用户目录、通知/审计等外部端口为测试替身；没有登录令牌、真实账号、短信或云请求。Core-only夹具不包含CRM部门模块，部门权限须单独验收。
- 正向：患者→自动初始疗程→原始表单→报告→同编号重试→禁止未复核直接审批→模拟复核/审批→训练计划→任务→启用→两个周期训练/疼痛变化→既有规则触发复核→转复评入口→治疗师显式新建复评→新报告。确认“转入口”本身不创建/完成评估，历史报告输入不被覆盖。
- 源变更：保存新模块后，同编号仍确认原报告；新编号才生成新版本与不同源摘要，旧输入保留，已关联评估删除拒绝。
- 错归属：治疗师即便能读两个患者，也不能把旧疗程或计划移给另一患者；不能把计划来源改为另一患者评估，不能删除计划正在引用的评估。
- 所有患者、备注与事件使用SYNTHETIC夹具；普通建档仍遵守原REAL默认，隔离夹具在本测试库明确标记来源，不把它当作现用分类捷径。上述模拟审批不代表真实临床签发。
