# S1-04 首批：报告版本并发和历史保留

2026-10-27。沿用原工作分支，AI 关闭；不改现用账号、患者、数据结构或已签发报告，不部署业务环境。这是 S1-04 的第一项修补，不等于患者→疗程→表单→报告完整业务验收通过。

## 根因及修补

原报告生成用 `selectListByAssessmentId(...).size() + 1` 作为版本。两个请求可读到相同条数；历史存在间隔或软删除时也可能复用旧版本。合成 H2 夹具复现已有 v1/v3 时旧公式仍得到 v3。

新增小型 `RehabReportVersionSequence`，在原报告创建事务内对当前机构的评估行加锁，再用锁定当前读取得最高历史版本并加一。包含软删除报告，不重新编号、不改历史原件，也不新增永久计数表或修改框架。无事务、缺租户、跨机构/已删除评估拒绝；异常或整数上限版本要求管理员复核，不进行覆盖。

MySQL 默认 REPEATABLE READ 下，调用者在等待前已有快照，单纯加锁后普通 `MAX` 查询仍可能读到旧值。所以最高版本查询也必须是锁定当前读。真实 MySQL 测试读取生产类中的 SQL 常量，在两个已建立空快照的会话中重现：第一请求提交 v1 后，第二会话的普通 COUNT 仍是0，但当前读正确取得v1，随后写v2。没有为了通过测试改数据库隔离级别。

普通报告生成的权限检查仍在分配前；生成、版本分配、报告保存与原有审计处于同一事务。异常回滚后可重新使用尚未提交的分配值，而不是制造一个已存在的报告版本。新增业务错误不包含病情、密码或原始报告内容。
