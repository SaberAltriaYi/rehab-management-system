## 2. 实际完成的技术验证

- 首次直接执行：**19 个检查中 18 个通过**，合成开户 HTTP400。根因是测试工具错误地将 `expiresAt` 设为 ISO 日期字符串，而真实 Owner→Core 接口明确发送 **Unix 毫秒时间戳**。修正测试数据后，正式机器接口、开户幂等、上限和授权同步的 37 项基础检查全部通过；没有修改 Core 产品源码以掩盖问题。
- 扩展到双机构真实 OAuth 登录后，发现**正式权限套餐对应的基础模板不包含 `rehab:motion:query`**。模拟机构可以开户、登录且拥有 `tenant_admin` 角色，但动作评估列表返回业务码 403。这个 403 是权限拒绝，不是跨机构数据泄露。
- 使用一次性 MySQL 中**新建的合成套餐副本**，只追加动作评估查询权限，保留原权限模板不变。用该合成权限套餐重新执行两家机构开户、真实登录、独立评估列表、伪造 `tenant-id` 头、跨机构详情访问和机器 API 测试，**56/56 PASS**。两家合成机构仅能看到各自的数据，跨机构记录详情被拒绝，伪造请求头返回业务 403。该实验**不代表批准生产权限扩大**。
- 安全边界通过真实 HTTP 验证：无 Token/错误 Token 均 HTTP401，非法申请 UUID HTTP400，合法 Token 可一次性开户，重复幂等键不重复开户，同键修改 Owner UUID、同 UUID 新申请号均 HTTP400，21 席拒绝，授权同步非本机构 UUID 与超过 20 席均拒绝，修订号过期不能覆盖新席位。
- 测试后检查所有随机容器与隔离网络均已删除；现网 Core 镜像 ID 仍为原有 `065ce5fa...`，正式数据库 036/36，SaaS 套餐与开户记录依然 0，Owner `test` 许可证 ACTIVE、20 席，Core `NOT_CONFIGURED`。
- 依据新发现更新 `desktop/scripts/owner-internal-pilot-readiness.mjs`，在原有正式套餐和机器通道门禁之外追加 `corePermissionPackageHasRehabMotionQuery`；纯函数新增缺失权限、缺失元数据时失败关闭的测试。全套 `node --test desktop/scripts/*.test.mjs` 现为 **129/129 PASS**，0 失败、0 跳过；迁移文件固定 SHA-256 核验通过。

## 3. 真实环境已确认的新阻断

Mac1 正式 `system_tenant_package` 中被 Owner 配置引用的权限套餐处于启用且未删除状态，但真实 `system_menu` 目前有效的 88 种 `rehab:` 权限中，该套餐**一项都未覆盖**（0/88）。其中 `rehab:motion:query` 明确缺失。仅检查 `package_id` 是否存在，会误把“不具备康复能力”的机构判断为已可开户。

正式只读开通工具现在会明确报告三项 `false`：

1. `effectiveCorePilotQuotaVerified`：正式 20/400/2000/5GiB SaaS 套餐尚未创建/启用；
2. `corePermissionPackageHasRehabMotionQuery`：正式套餐缺少必要的康复动作评估查询权限；
3. `ownerCoreMachineChannelReady`：机器 Token 一致性及双端开关尚未通过。

其余审批、20 席、`rehab` 授权、唯一申请、未绑定现有 Core 租户等门禁均维持通过。**本轮没有执行正式权限更改；不应在现网给 111 套餐一次性追加全部 88 个康复权限**。继续沿用已有 037 权限影响约束：管理员新增 10 项、治疗师新增 8 项，需要先做准确权限矩阵和必要的审批，再执行有备份及回滚的部署。

## 4. 结论及限制

**C2 候选的隔离机器 API、合成开户幂等及双租户数据隔离验收通过**。该结论仅适用于运行上述 C2 镜像、隔离 036+V3/V4 数据结构、具备最小动作查询权限的**合成套餐**。

它不是 Owner→Core 正式联动验收：正式 Core 仍旧镜像，正式 SaaS 套餐没有创建，正式权限套餐无法使用康复模块，机器通道未启用；未进行候选前端/微信客户端/HEP 联动、正式 TLS 分发或临床人工验收。因此继续维持 **NO-GO**，不能打开现网开户或导入真实患者。
