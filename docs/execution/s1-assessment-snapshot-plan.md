# S1-04 下一项：评估内容修订与报告源快照一致性

2026-10-27，待实施，不算验收。先核对登录刷新及摘要隐私批次的最新提交/CI；仅在本地隔离合成数据库中复现并修补，不能用现用临床资料试错。保持原分支/AI关闭，不改上游包名、不换数据库、不覆盖旧报告。

## 实际代码发现

- `RehabReportServiceImpl.generateReport` 在报告锁之前先读主评估及权限；带requestKey时`findCompleted`内部锁评估，而不带编号路径到读取患者、疗程、模块之后才调用版本锁。版本不冲突和请求不重复，并不能证明内容来源一致。
- `RehabAssessmentServiceImpl` 的更新、模块保存、删除、归档及派生状态刷新目前不共享报告使用的评估锁。主记录与模块虽在同一写事务中，读取先后仍可能遇到旧快照或不同提交，必须真MySQL REPEATABLE READ证明，不能只测H2。
- 主评估DO没有临床内容修订计数。模块的`version`主要是表单/协议版本，不能冒充编辑修订号；报告`reportVersion`也不等于源评估修订。旧报告已经有结构化payload/版本快照，应保留原件，不能回填捏造历史来源。
- 还需核对患者/疗程元数据、附件及任何派生写入的事务/锁顺序；患者治理已有患者锁，不能引入“报告先评估后患者、另一路先患者后评估”的死锁。AI默认关闭，不为验收启用它。

## 实施顺序

1. 清点所有写入口、SQL、原权限/状态限制及现有快照字段，画最小锁顺序；检查AI域等读取者是否实际写评估，不能仅凭导入Mapper就下结论。
2. 先加确定性合成回归：生成与更新/模块保存竞争、旧RR快照等待锁、删除/归档竞争、两名治疗师并发保存和重复请求回放。每个测试明确原字段、版本、审计、身份和事务回滚的预期；原算法应先复现风险。
3. 统一写入口和生成入口的事务协调，权限仍在回放前验证，获取锁后必须读取当前源数据。仅加行锁不会刷新已经建立的RR普通读快照；不能把先前读到的DO继续当作最新内容。患者/疗程/附件也按已核对的依赖处理，避免未经证明的大范围锁。
4. 先保证一次生成所用源数据可明确冻结，再确定是否需要最小追加迁移实现临床编辑修订号和乐观冲突提示。若需要：追加037及固定账本、显式旧数据未知基线、升级/恢复测试；不更改020–036或给旧报告假造版本。不要在复现前先修改患者结构或全局事务隔离。
5. 报告新版本保存来源修订/稳定内容摘要与实际原始数据映射，后续评估修改只能生成新修订，不改已审核原件；同UUID重试继续返回原结果而非新评估的结果。UI应区分“确认旧请求”与“基于新数据生成”。
6. 增加过期编辑冲突/刷新提示、原权限/跨机构/归档/审批反例及所有专项表单回归。合法0、负数、单位/轴/来源必须保真，未知/缺失不自动推断完成或临床结论。

退出：纯单元/H2、真MySQL并发、全后端、管理端构建/类型/审计、合成完整患者→疗程→专项表单→报告→训练→复评均分别留证；再推进S1-05/06。正常浏览器身份/验证码及临床签发仍独立，不关闭验证码、不借令牌、不自动升级业务环境。

另保留数据质量风险：静态/NASM旧解析路径对非法JSON字符串返回空对象，本批摘要隐私修补只去敏、保留该旧语义；后续应通过显式输入校验与可恢复错误治理，不能把本批称为所有来源数据已保真。合法数据的数值/备注不变性已另测。
