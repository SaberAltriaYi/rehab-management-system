日期：2026-10-26。交付性质：产品、架构与实施规划；不是已完成开发或生产上线声明。本轮没有修改业务代码、运行配置、账号、患者数据或已有部署，没有注册竞品账号、上传资料、联系销售或购买服务。

## 一、决策摘要

**建议把现有多仓库收敛为“一套面向运动康复工作室的产品、三个业务工作区、一个独立拥有者控制面”，而不是继续增加互相分离的后台。**

三个工作区分别是：机构业务与康复 Core、运动评估与报告、患者家庭训练 HEP。CRM、会员和员工经营属于机构业务能力；不要各自再维护一套患者、一套登录和一套全量动作库。Owner 独立管理机构授权，不与临床管理混成超级入口。

产品定位建议为：**面向儿童青少年体态与基础运动能力、青少年专项运动员及成人运动康复的工作室运营与康复交付平台。** 核心差异化假设是本地/可控部署、中文专项流程、可追溯运动证据、治疗师复核、双版本报告和 HEP 执行回流，不是动作数量最多、自动诊断或大型医院 HIS 替代品。该差异化需要真实用户验证，不能宣称市场已经证明。

最先投入：身份和业务闭环 → 工作流 UI → 证据报告 → 动作库质量 → 可验证算法 → 稳定部署。多机构商业化、复杂 ERP、全自动 AI 处方后置。

## 二、范围、方法与限制

- 本轮建立 **31 个条目的比较地图：29 个产品/品牌条目和 2 个技术底座**，涵盖 7 类；这是定向覆盖，不是市场全量名录，也不是 29 家独立公司。
- 以官方网站、厂商帮助中心、开发者维护的应用商店说明及官方代码仓库为证据。不以评论网站排名、推广软文或论坛体验作为产品事实。
- 没有登录付费产品或做实机试用。因此“官方描述提供某能力”不等于已验证其易用性、算法准确性、服务 SLA、完整 API、在中国的可用性或合规性。
- 不给未实测产品打伪精确分数、不估造市场占有率，不把页面未提及某功能判作该产品没有该功能。
- 国内部分产品的公开资料较少，仍需演示、试用、接口与商务核实；本轮未取得报价。国外 RTM/保险结算能力不能直接复制到国内工作室。
- 旧品牌合并处理：Wibbi 原名 Physiotec；Prompt 官方说明 PT Wired 等业务已转为其品牌能力；Kaia 官网明确宣布加入 Sword。保留产品条目以比较流程，不据此重复统计独立竞争主体。

## 四、最值得深入体验的六组对象

下一轮演示优先级为本项目的工作流匹配判断，不是市场份额排名：

1. **FMS Pro**：核对专项操作顺序、缺项提示、评分追溯、报告到纠正训练。
2. **Rehab Guru + Jane/Cliniko**：分别体验业务/HEP一体化与工作室日常日程/患者工作区。
3. **Physitrack + Medbridge**：体验开方速度、患者如何进入本人方案、疼痛/反馈和复核。
4. **HumanTrak + Kinetisense**：体验固定测试协议、重复识别、质量提示及解释层级。
5. **三体云动 + 微健**：体验服务卡、约课、到店核销、冻结/退款、教练工作量；不照搬临床无关模块。
6. **术康 + 一个国内康复信息平台**：核对中文专业路径、院外随访和机构协同。

统一用虚构成人档案、同一预约/评估/训练脚本对比，记录操作步骤、出错恢复、角色可见范围、导出、接口与隐私条款。不上传真实患者，不因试用而默认订阅或授权数据跨境。当前未执行这些付费/登录试用。

## 六、整体产品应该怎样构建

### 6.1 一套产品，而非一个巨大新仓库

建议先保持现有仓库，不进行强行全量合并或更换框架。统一产品导航、设计规范、主数据关系、接口契约和发布清单；是否以后采用单仓库，在稳定之后再评估。

```text
工作室员工 Web / 平板
  └─ 统一机构业务入口（现有 Core）
       ├─ 今日工作、预约与患者/疗程工作区
       ├─ 康复评估、报告、训练、复评
       ├─ CRM 部门流转、会员权益、员工经营
       ├─ 专门权限 → 运动工作区 → 复核快照收件箱
       └─ 机构内 HEP 开方、执行观察与风险复核

  └─ 正式认证 → 本人授权方案 → 执行/反馈（HEP）

Core ↔ 有版本的 API / 幂等事件 ↔ HEP / 运动服务
```

| 商业权益、服务次数与到店履约 | Core 的会员/服务权益域 | HEP 保留所需状态/快照；冻结/过期时历史与风险仍可访问处理 |
| 动作内容与训练模板 | HEP 为动作内容主库，Core 保留明确 ID 映射 | 先审核、再处方引用；停止双向随意覆盖内容；版本变更不改旧处方 |
| 计划执行、组次、疼痛/RPE、反馈和风险 | HEP | 幂等回传 Core，治疗师复核后支持复评，不自动写临床结论 |
| 原始资料、派生运动学、图帧、分析修订 | 运动工作区 | Core 保留来源摘要/版本/状态；大文件私有按权访问，不在接口反复复制全量 |
| 已签发临床报告与修订历史 | Core 为正式归档索引；工作区提供有来源版本的素材/草稿 | 新草稿或新算法版本不能覆盖旧签发件；过渡期明确哪条流程签发，不能要求用户跨系统重复批准同一报告 |

登录建议：统一员工业务入口与明确权限的短期服务交接；患者与监护人是独立身份和授权关系。Owner 不并入普通 SSO。现有会员认证和患者邀请能力继续利用，先补接口/前端/会话与真实身份校验闭环，不重写成另一套万能账号。

### 6.3 构建和交付

- 继续 Java 模块化 Core、Vue 管理端、独立 HEP、Python/OpenSim 工作进程及 Tauri 启动器；首版不新增 Kubernetes、服务网格或分布式数据库。
- 将算法领域拆成纯计算边界：解析/规范化、质控、事件、数值、证据、报告；UI 和 API 不复制计算公式。研究代码通过受控适配纳入生产，不复制整个研究平台。
- 使用现有持久队列、inbox/outbox、修订和乐观锁；补取消/恢复、幂等、人工重试、对账和运行状态，不另造同功能集群。
- 建立 `release-manifest`：各仓库 commit、构建摘要、接口/算法/模型/模板版本、迁移清单、模块开关与回退兼容关系；跨仓统一的是发布，不是复制源码。
- 正式入口使用生产构建和受控 HTTPS 网关；当前开发端口不作为最终用户地址。局域网内部版和患者居家远程版是两个网络边界，不能仅把 127.0.0.1 改成 0.0.0.0。
- 本地模式保持患者资料和原视频在工作室；远程患者模式须明确有认证网关/托管服务的部署、信任、文件、备份与撤销策略，不能假定本机离线也能持续居家服务。

## 八、UI 不应只是加图标

建议一级导航收敛成：**今日工作、客户/患者、评估与报告、训练与随访、经营管理、系统设置**。按角色实际显示；Owner 在独立界面。保留旧入口映射，避免一次性改路由导致书签、权限或用户习惯失效。

1. **前台/运营**：预约日历、到店、待联系、待认领、转接；不展示临床敏感摘要。
2. **治疗师**：今天患者、待评估/报告、家庭训练异常、复评；从患者进入，不从 15 个功能标签里找入口。
3. **机构负责人**：容量、服务履约、风险未处理、经营趋势；指标能到明细，不是只做大屏。
4. **运动工作区**：顶部患者/试次/质控；左侧文件和任务，中部视频/原生模型，底部/右侧全坐标曲线与事件；提供简洁视图和专业视图，不隐藏原数据。
5. **患者/家长**：今天做什么、如何做、做到多少、如何反馈、何时联系治疗师；不显示复杂模型、管理员术语或全量动作搜索。

统一加载、空、失败、无权、保存中、已保存、待复核、已签发状态；自动草稿可恢复但修改要失效旧解读。移动端触控、可访问标签、键盘、单位、颜色非唯一表达及错误可修复优先于动画/装饰。

现场 Web/平板和患者 H5 先完成，再做微信小程序真机；FMS Pro 的浏览器/主屏方式提供了“先优化网页任务”的参考，不证明本项目可免做移动验收。桌面安装器是部署工具，不再重做业务管理页面。

## 九、算法升级应该怎么走

### A0. 保真和质控

原始文件与来源哈希不变，明确采样、单位、坐标类型、模型/网格、校准、遮挡、缺失与视频同步。原始曲线全保留，处理结果单独版本化；未知耦合量不硬转临床含义。时间轴一致不等于物理同步已批准。

### A1. 动作事件与纯量化

先在深蹲/单腿蹲等有实际协议和标注基础的动作上做重复/分期候选、幅度/峰值/时刻、左右差和重复稳定性。复用研究引擎已有分期/纯计算代码须通过差异与合同验证；当前工作区起止/极值不能直接称为已验证的落地或步态识别。

保留精确秒轴和采样索引；0–100% 周期曲线仅为派生比较。滤波、短缺口修复、速度/加速度须有明确参数、噪声评估及不适用条件。近零分母、左右正方向未确认或不同协议时不输出误导性对称比例。

### A2. 临床规则与三类人群

先为每个结果登记：输入、公式、单位、协议、适用人群、来源与版本、必需人工观察、缺失处理和复评可比条件。儿童青少年、专项运动员和成人康复分开；不得使用成年人常模套儿童，也不从一个样本建立百分位。

FMS/NASM-CES/SFMA 现场评分与运动学派生量并列显示，缺现场条件不补造评分。报告区分实测/模型估计、规则推断和人工意见；临床参考标准与软件单元测试是不同的证据。

### A3. 标注和验证资产

建立合成边界集、获授权的真实金标准样本、独立留出集和治疗师标注工具；记录事件误差、漏检/误检、重复性、评价者一致性、校准失败与人群覆盖。先冻结评价方案再迭代算法；不能用反复调过参数的同一批数据做最终准确率证明。

当前已核对的一名受试者多试次仅支持该输入的软件保真检查，不足以声称算法适用于全部人群。若没有力台/可信动力学输入，不把角度推成实测力或负荷。竞品的参考数据库、评分和清除/认证声明不能借用。

### A4. 可选 AI 只做草稿

先完成确定性的图文报告和人工复核。自动云端 AI 继续默认关闭；将来启用必须有资料/用途授权、未成年人监护授权、最小化、来源绑定、服务方数据政策和撤销处理。AI 不补数值、不代签、不自动更改处方。不为追赶竞品“AI”标签牺牲数据真实性。

## 十、建设/购买/接入的取舍

| 类别 | 推荐 | 原因 |
| --- | --- | --- |
| 患者/疗程、权限、部门、复核及版本归档 | 保留自研并完善 | 是已有资产和数据边界；换完整底座的迁移成本高，当前未证明值得 |

整体目标可以是约 **10–14 周形成可供决策的内部稳定版与受控试运行结果**，不是完整临床有效性或商业 SaaS 同期保证。若只有零散投入，应按阶段拆小，不给固定自然日承诺。前一版计划只针对已有系统收尾，本方案增加了竞品验证、平台产品整理和经营边界，范围更大。

建议人员职责：技术负责人负责接口和版本/迁移；前端负责角色任务与手机；QA/DevOps负责可重复验收/恢复/制品；治疗师负责人负责协议、动作、标注与报告审核。一人可兼任工程角色，但不能用自动化测试替代临床负责人。

### 最近两周应开工的具体任务

1. 更新产品/目录索引，标出正式入口、研究来源、旧兼容入口；两份引擎只做比对，不立即合并删除。
2. 用同一虚构案例制定竞品演示脚本，并与 3 名实际治疗师核对当前最大操作阻力。
3. 完成患者登录与绑定的设计/威胁模型及端到端用例，复用现有后端，不用弱身份捷径解锁。
4. 定义患者360/疗程时间线和角色首页的低保真流程，冻结一级导航后再改页面。

7. 固定联合发布清单和测试环境；对开发端口、可变镜像、恢复证据和过期文档逐项登记。

## 十二、怎样判断优化是否有效

下表是拟采集指标/目标，不是已经测得的经营提升；先取得基线再比较，排除模拟患者和开发任务。

| 判断问题 | 指标定义/验收方法 | 初步目标或规则 |
| --- | --- | --- |
| 治疗师是否更省操作 | 固定案例的建档→完成评估→草稿报告耗时及失败步骤 | 先测现状，再订改善目标；不照搬竞品宣传的两分钟 |
| 患者是否真正进入训练 | 已下发有效计划的人中，成功登录并开始本人Session的比例 | 分母/排除到期/测试账号规则固定；不能用网页访问数替代 |
| 依从性是否可信 | 已到期且应执行的处方组次中，患者实际提交且未撤销的完成组次 | 区分未执行、未上报、休息日、暂停；到店签到不算家庭训练 |
| 风险是否处理 | 待复核事件到首次处理和关闭的时长、逾期明细 | 高风险规则/服务时段由临床负责人确定，不能靠短信发送数结案 |
| 评估是否可交付 | 有效输入在约定硬件/包预算下导入到可复核草稿时长 | 用户目标约60分钟；3并发/队列基线实测后才承诺百分位 |
| 数值是否保真 | 原始/派生值、单位、事件、报告来源和版本一致性 | 合成精确值、授权真值对照、独立留出验证分开报告 |
| 发布是否稳定 | 关键流程失败、升级后回归、恢复耗时和数据差异 | 必要测试零失败，跳过逐项审查；备份必须能恢复 |
