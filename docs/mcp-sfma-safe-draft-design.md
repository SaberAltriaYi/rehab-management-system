## 已读代码与确认结果

1. `src/views/rehab/assessment/create/index.vue` 共用创建和编辑路径。
   - `submitForm` 先进行患者、Episode、类型、日期的基础校验。

   - `patientId` watcher 会清空并重新选择 Episode；详情加载也逐项设置 patientId/episodeId。需要测试异步 watcher 是否覆盖原评估的非当前活跃 Episode，不能假设恢复总是正确。
   - 已有 dirty-state 比较，但本次读取区域未见离开保护；需查全文件及共用路由机制后确定实现位置。
2. `components/forms/SfmaForm.vue` 当前 `validate = async () => true`。
   - **修正先前笼统假设：不能把 SFMA 不完整草稿问题直接归因于量表必填验证，也不需要为了草稿绕过所有校验。** 其他量表另行调查。
   - getFormData 同时输出顶层内容和嵌套 sfma 内容。改造前须核对历史兼容和后端读取规则，不能直接删除其中一层。
3. `RehabAssessmentServiceImpl`：
   - create/update 已接受显式 draft 的保持逻辑。
   - 独立 module-data/save 仍使用不保留显式 draft 的派生状态刷新；自动保存接入前必须解决所有入口的一致性。
   - ensureAssessmentEditable 当前仅拒绝 archived；reviewed 的修改权限与历史修订仍需设计，不能宣称已确认评估不可覆盖。
4. 控制器中已定位 create/update/delete/archive/module-data/save 等入口及相应操作权限。患者级权限和租户条件继续在服务/DAO 路径核对。控制器初次搜索截断，附件及其他方法须补全，尚不构成全入口覆盖证明。

## 首批最小实现边界

先实现可验证的手动草稿保存/恢复安全，不立即增加定时器或本地持久化健康资料。

- 必要身份与结构校验保留，完成评估另做临床项目完整性检查。
- 保存入口同步加重入锁，校验失败必须释放；不在请求未完成时发送第二次创建。
- 保存使用不可变请求快照；响应成功只能确认对应快照，之后的输入仍为未保存。
- 编辑已有评估时禁用切换患者的 UI，同时保留已实现的后端患者归属拒绝。
- 恢复数据使用明确 hydration 标记，避免患者 watcher 改写历史 Episode。
- 未保存离开需确认，保存失败不得重置数据或跳转。
- 页面内避免重复请求不等于服务端幂等，跨设备/网络重试仍待下一批。

以上预期可先做到无 Schema 改动；需通过实际源码与测试核实后才实施。

## 下一批：revision 和自动保存（设计候选，不是已执行迁移）

拟采用评估聚合级 revision：成功修改通过条件更新比较期望版本；所有改变评估内容或状态的写入口共同参与并在事务中处理。仅给 create/update 加锁而 module-data/save 不检查，会留下覆盖漏洞。

实施前必须提交确切设计：

- 现有表/DO/mapper 是否已有可复用版本字段；没有时列出新增列、类型、默认值、旧数据初始化策略。
- 在条件更新成功后才更新模块；发生冲突不得保留部分修改。
- 创建/确认幂等键作用域、唯一约束和同键不同内容拒绝行为。
- 旧客户端没有 revision 时的兼容与拒绝策略，不允许静默退回覆盖写。
- API 响应提供可识别冲突码和新版本；客户端保留本地输入供人工解决，不自动覆盖服务器内容。
- 发布顺序、应用回退兼容期、保留新业务数据的前滚/回滚方案。

revision、幂等和完整写入口审查完成前，不发布自动保存。自动保存之后才补去抖、串行保存、保存状态和弱网恢复。
