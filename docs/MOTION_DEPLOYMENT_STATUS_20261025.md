## 阻止业务切换的实际问题

现有原生数据库缺少 `internal_schema_history`。对比发布清单还发现部分历史增量表不存在，不能假定所有历史版本均已执行。部分缺表属于本机未交付的可选模块，不能仅凭缺表数量判定正在使用的康复功能异常；但同样不能给它们补写“已执行”记录。

当前 `deploy/internal/migrate.sh` 的数据库适配针对 Docker Compose 部署；不能直接用它操作本机原生 MySQL。必须先建立经过审计的本机升级路径，而非指向另一个旧测试容器来制造迁移通过。

因此本次**不切换业务后端、不向业务库执行 032/033、不补造历史账本、不重跑初始化脚本**。主系统原业务仍运行，已构建的 JAR 和界面并不代表业务后端已加载新代码。

尤其禁止对旧库重放：

- 初始建库 SQL 中的 `DROP TABLE`；
- 演示数据清理；
- 初次部署账号停用/轮换；
- 用修改历史校验和来消除状态差异。

## 推荐的下一项独立变更

在已验证备份的独立副本上，进行旧库基线接管专项：核对实际表、列、索引、约束及安全状态，区分已交付和未交付模块；逐项设计仅增量、不清数据的补齐脚本及原生数据库适配，形成真实基线证据后再登记。完整回归、核对患者及附件计数后，安排短暂停机切换，并保留旧库及程序以供恢复。

这会扩展到既有数据库历史治理，不只是给运动模块新增两张权限记录；应作为明确的升级任务安排，不能在容器清理过程中顺带隐式执行。
