# RuoYi 上游模块恢复兼容性报告 V1.0

日期：2026-09-20。

项目基线：`995247148d9e8d90237ed648ab50c443f708fac8`（GitHub master）。

上游共同祖先：`d3400b70d61fca76e14be8255f9fc188dfff6e81`，POM 标识 `2026.01-jdk8-SNAPSHOT`、Spring Boot 2.7.18。

配套主报告：`docs/mcp-rehab-audit-roadmap-v1.md`。

**结论：允许开展逐模块恢复设计，不批准现在直接恢复任何模块。特别是 CRM 依赖 BPM，模块恢复会使原内部版安全接受条件发生变化。**

## 1. 审计口径

一个模块需要同时核对五个状态：

1. 源码是否存在；
2. 是否在父 Maven reactor 构建；
3. 是否进入 yudao-server 运行依赖；
4. 数据库表、种子、权限和菜单是否在目标环境正确迁移；
5. 前端路由/页面/API 是否完整且允许访问。

源码存在、菜单存在、父 POM 没注释，均不能单独证明运行时已启用。SQL 文件存在也不能证明生产库已执行。本轮未启动恢复后的应用或连接生产库，所有可行性为有条件静态判断。

## 3. 上游差异和恢复边界

相对固定上游基线，本项目 33 个提交领先、0 个落后；不是相对今日所有上游分支的实时结论。完整 tree 对比为新增 2,243、修改 46、删除 2 个文件路径。

需保留的定制边界：

- `yudao-module-rehab/` 的患者/评估/训练/报告和权限。
- `yudao-framework/`、system/member/infra 已有安全补丁。
- server 内部专用配置、模块装配边界。
- 康复迁移账本、租户/关系约束和菜单限制。
- 前端内部版入口、康复路由及桌面/局域网部署。

恢复时不得直接复制最新上游 POM、application 配置或全库初始化 SQL。先记录所复用源码的 SHA；同基线恢复优先于大版本升级。若最新上游安全修复需要 JDK/Boot 跨代，作为独立技术迁移项目评审。

## 4. CRM：优先级高，依赖与业务改造风险中高

### 4.1 可复用内容

已有客户、联系人、线索、跟进、负责人、权限、商机/合同/回款源码；前端资源较完整。康复已有 `rehab_patient_crm_binding`，包含 patientId、crmCustomerId、绑定/同步状态及时间。

但这只是桥接：`CrmCustomerDO` 以姓名、mobile、telephone、industryId、level、source、ownerUserId 等为主，不能承载完整个人康复/监护/出生信息。

### 4.2 技术阻碍

- `yudao-module-crm/pom.xml` 直接依赖 system、infra、**BPM**。加入 server 依赖可能把 BPM 相关引擎和 API 一起带入。
- `RehabPatientServiceImpl.java:680-699` 通过 JdbcTemplate 查 CRM/member，查询没有 tenant 条件，不受 MyBatis 租户拦截器自动保护。
- 绑定检查当前主要关注已有冲突，不是完整的目标身份/租户授权流程。
- 父 POM 包含 CRM，但内部 server 明确不交付它；不能仅恢复菜单。
- 旧数据库可能已有 CRM 表/桥接 bootstrap，需核对信息架构和升级历史，禁止重复导入整套种子。

### 4.3 推荐首期范围

个人潜客 → 咨询 → 跟进 → 预约/到店 → 体验/初评 → 成交/正式客户。

复用跟进、归属和访问控制。默认不开放全套 B2B 合同审批、复杂回款预测。联系人/监护人允许与受评估人不同；不能把儿童和付费家长合为一人。

### 4.4 两种可选技术路径

A. 恢复 CRM 与其必要 BPM 依赖，但只开放最小 API/菜单；需要重新扫描依赖、限制引擎入口并验证启动和租户行为。

B. 在确认调用点后将 CRM 的 BPM 依赖隔离为可选适配层；改动更细，但不能只在 POM 排除依赖而留下缺失 Bean。

实施前以编译依赖树、实际 Bean 装配、审批相关服务调用分析选择，不在审计阶段凭空认定哪种无风险。

### 4.5 恢复验收

- 一个真实人有稳定统一身份，历史 patientId 不变；重复候选人工确认。
- CRM 前台看不到未授权的疼痛/病史/视频/报告。
- 跨租户/跨负责人绑定和读取被拒绝。
- 关闭 CRM 后康复核心仍能建档、评估、导出和训练。
- 新增依赖安全扫描和备份/回滚方案通过。

## 5. ERP / 库存：P2，有复用价值

现有 ERP DO 涵盖产品/单位、供应商、采购订单/入库/退货、销售订单/出库/退货、库存/仓库/流水/调拨/盘点及财务账户/收付款。POM 直接依赖 system，以及 web/security/mybatis/redis/excel 基础组件。

推荐只先交付：训练器材/耗材目录 → 采购 → 入库 → 领用/出库 → 库存 → 盘点。低库存预警需核实现有规则或定向补充，不凭源码目录承诺已有。

恢复清单：

1. 核对 ERP schema 与当前 DB 字段/索引/租户差异，明确新增脚本。
2. 加回构建和 server 依赖，检查依赖冲突与启动。
3. 前后端 API 和权限串联，按岗位只开放需要的菜单。
4. 验证并发扣库存、盘点调整、反审核、重复提交、精度和负库存控制。
5. 历史库存数来源确认，不用随意种子作为真实期初库存。
6. 财务账户、销售客户若启用需与统一 Client/机构账务边界对齐，不形成第三套个人主档。

固定资产与耗材分别建模。设备唯一编号、维修/停用/报废是资产生命周期，不应靠重复出入库记录模拟。

## 6. WMS：先复用 ERP，不另造一个仓库系统

当前没有证据表明本基线存在独立 WMS 可恢复。已有 ERP warehouse/stock/move/check 是轻量库存基础。

库位、批号、效期、序列号和领用到客户/训练记录的追踪，只在业务确实需要时增加；不第一阶段引入波次、自动化仓储、复杂供应链。

## 7. BPM：依赖评审先于产品开放

价值：以后用于采购审批、退款/特殊优惠、重要报告发布或机构规范工作流。

风险：增加引擎 schema、任务/定时器、组织权限和历史流程数据；流程版本升级不是简单页面开关。

第一阶段评估的草稿→待确认→完成/修订用业务状态机即可，不引入审批引擎来解决自动保存。若 CRM 技术依赖带入 BPM，也需默认隐藏非交付流程和 API。

## 8. Report：不要替换康复报告引擎

`yudao-module-report` 属上游报表能力；`rehab_report`/`rehab_report_version` 是康复业务报告。两者不同。

优先保留已有 DOCX/PDF 服务，抽离确定性 Context Builder 支持 ChatGPT 导出。经营报表以后再做患者生命周期、预约到店、续费、疗程执行、库存消耗等指标。

恢复前审查报表数据源权限、动态 SQL、文件导入和 dashboard 分享；禁止报表引擎持有无限范围生产数据库权限或默认向前台开放健康明细。

## 9. Member / HRM / 财务边界

Member 已加入 server。开放患者/家长侧前验证 rehab_patient_user_binding、监护关系、账号注销和历史访问撤销；一个患者可有多位合法监护人，一个账号也可能照护多人，不能机械假定永久一对一。

HRM 不应从未存在的模块“恢复”。system 用户/部门/岗位继续复用；业务上先排班与资质。薪酬、劳动合同、人事档案属于另一个敏感权限域。

财务 FMS 需先明确所指。不要把临床 FMS（Functional Movement Screen）的模块代码/权限用于机构财务。

## 10. 共同数据库与安全门禁

- **先处理主报告 R01/P0：升级链可执行全业务清理脚本。** 在此之前不尝试恢复 CRM/ERP 表。
- 旧账本缺失不自动 baseline；无对应迁移记录也不说明可安全重放初始 SQL。
- 当前 schema 中补租户列默认 1，恢复前核验历史数据归属。
- 不能因 DO 不含 tenant 字段就判定租户无效；但所有 raw JDBC、自定义 SQL、后台 job 和导出必须单独验证。
- `deploy/internal/SECURITY_RISK_REGISTER.md` 的历史接受条件明确要求 CRM/BPM 等持续关闭。恢复后该接受不能继续直接套用。
- 当前 LAN 限定不是防护替代品。公网/第三方上传/大文件预览进一步扩大攻击面，必须重新评估支持基线和权限。
- 数据库备份、文件备份、配置版本、迁移账本需一致恢复点；所有恢复先在隔离环境演练。

## 11. 推荐恢复流程

```text
确认目标版本和数据现场
 → 只读 schema / 账本 / 模块依赖审计
 → 明确业务最小范围与身份/权限契约
 → 用户批准迁移和依赖方案
 → feature branch
 → 隔离数据库与合成/脱敏数据
 → 后端装配 + API + 前端 + 菜单权限
 → 数据迁移演练 + 回滚/前滚演练
 → 单元/集成/安全/E2E/依赖扫描
 → 治疗师与前台试用
 → 独立 PR / Commit
 → 经批准发布
```

不在主分支取消一批注释后“看能不能运行”；不在真实库试错；不自动 merge 最新上游。

## 12. 逐模块 Go / No-Go 决策表

| 条件 | CRM | ERP/轻量库存 | BPM | Report |
|---|---|---|---|---|
| 身份/业务边界 | 统一 Client 先批准 | 资产与耗材先区分 | 确定真实审批流 | 指标及数据授权明确 |
| 依赖门禁 | BPM 调用与 Bean 装配通过 | 完整依赖树及库存事务通过 | 引擎/任务/租户通过 | 数据源/动态查询风险可控 |
| DB 门禁 | bridge/客户/权限迁移清楚 | 产品/仓库/库存初始量有来源 | 流程 schema 与版本可迁移 | 不无限授权数据源 |
| 安全门禁 | 不泄露健康数据、跨租户拒绝 | 最小采购/库存权限 | 非交付 API 不开放 | 无公开健康详情/导出 |
| 测试门禁 | 客户生命周期完整 | 入库领用盘点闭环 | 流程升级/撤销一致 | 权限裁剪/数值口径正确 |
| 当前决定 | 暂不启用，进入 P1 设计 | 暂不启用，P2 | 暂不单独启用 | 暂不启用 |

## 13. 本轮结论

康复系统没有脱离上游整体架构，应以同基线模块复用为主。但“恢复”必须同时处理产品适配、Client、权限、迁移和安全，不是取消 POM 注释。

本轮未恢复任何模块、未改代码或数据库、未进行版本升级，未产生 AI Token 费用。后续实施须等待用户确认主报告路线及具体模块计划。
