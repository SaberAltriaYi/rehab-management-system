# 康复管理系统整体框架与 OpenCap 双机评估可行性方案

**核验日期：**2026-09-26（Asia/Shanghai）
**对象：**`/Users/saber/Documents/playground/rehab-module-enable-clean`，即「运动康复评估与业务管理系统」；不是工作区顶层的 Python `rehab_reporter`。
**工作边界：**本轮只读项目文件、官方说明、公开源码和研究文献；未连接 OpenCap 账号或患者库，未采集/上传患者视频，未运行构建或测试，未修改业务代码。本文是架构与可行性审查，不是临床验证、商用授权或上线许可。

## 一、先给结论与产品边界

1. **整体路线：沿用 RuoYi Vue Pro 模块化单体，不重做患者、评估、报告或训练系统。**让患者/康复周期 Episode 成为业务主线；外部测量设备和 OpenCap 是评估证据适配器，不是第二套患者主库或自动诊断引擎。
2. **OpenCap 双机运动学接入技术上可行，但须分层理解。**官方多机方案需要至少两台独立 iOS 设备、另一个运行 Web 界面的设备、标定板和稳定网络；“一台手机的双镜头”不等同于两台经过外参标定并同步的采集设备。官方可生成 3D 运动学/OpenSim 数据；步速、步频、步长等可在官方处理库的后处理代码中计算，不代表本项目已经具备自动采集或判读。[2](https://www.opencap.ai/get-started) [3](https://www.opencap.ai/) [OpenCap gait_analysis.py](https://github.com/opencap-org/opencap-processing/blob/main/ActivityAnalyses/gait_analysis.py)
3. **对商业康复门店，现有 Stanford OpenCap 公共云是当前的硬性 No-Go。**其现行服务条款仅许可学术/非营利机构的非商业研究或教育用途，明文禁止任何商业实体使用，包括商业实体的研究；并称所有数据（包括视频）对开发团队可见且可能用于算法开发。不能以“视频不公开分享”或“先用几个真实患者试试”绕过这一限制。必须先取得书面商用服务授权与数据处理约定，或完成独立处理链的许可、设备与安全可行性审查。[1](https://www.opencap.ai/terms-conditions)
4. **“自动量化”与“自动临床判断”必须分开。**首期仅自动生成可追溯的运动指标与质量提示，由治疗师核对；不要自动给出 SFMA/FMS 分数、疾病诊断、伤病风险结论或处方。文献显示较可靠的是部分下肢、矢状面以及深蹲/步行等受验证任务，对临床人群、踝/骨盆及复杂动作的表现不一致。[1](https://www.frontiersin.org/journals/digital-health/articles/10.3389/fdgth.2026.1882536/full) [10](https://journals.plos.org/ploscompbiol/article?id=10.1371%2Fjournal.pcbi.1011462)

## 三、目标整体架构（在现有系统内渐进扩展）

```text
治疗师管理端 / 已授权的员工移动端 / 桌面启动器
       │                    患者端：认证安全门禁通过前关闭
       └── Nginx HTTPS → yudao-server（现有认证、RBAC、租户、患者范围）
                           ├─ system / infra：人员、授权、审计、文件与运行配置
                           ├─ rehab：Patient ↔ Episode → Assessment → ReportVersion
                           │                      ↘ CarePlan → Task → Checkin → Progress/Reassessment
                           ├─ 机构业务：CRM/BPM/ERP/Member/Report（逐模块 opt-in 验收）
                           └─ 评估证据适配层（不另建患者库）
                                 ├─ SFMA/FMS/YBT/静态评估/Visbody
                                 └─ OpenCap：Session/Trial/RawAsset → QC → DerivedMetric → 人工确认
                                           │
                                           └─ 合法来源文件导入（优先）/获授权供应商接口（后续）

MySQL：业务关系、同意/版本/审计、任务状态、派生指标
受控文件卷或对象存储：视频及 OpenSim 文件，哈希、保留期、授权下载
可选隔离科学计算 Worker：只处理被授权文件；不共享后台账号/患者主库
```

### 3.1 业务子域与边界

| 子域 | 责任及关联 | 不做的事 |
| --- | --- | --- |
| 身份/患者/机构 | 保持 Patient ID 与 Episode 历史外键；CRM/Member 渐进关联、人工去重；角色/租户/患者范围后端强制执行 | 不以手机号自动并人；不让前台/销售看到无关健康视频 |
| 评估与原件 | 评估协议版本、手动草稿和状态机；Session/Trial/标定/文件、数据质量与来源独立存档 | 不将 OpenCap 原始数据覆盖人工记录，不因没有可选视频拒绝评估 |
| 临床审核/报告 | Raw → Parsed → QC → Derived → ClinicianConfirmed → ReportVersion；报告清楚标识“自动测得/人工确认/数据不足” | 不让算法或外部 AI 直接把评估置为 `completed`、写确诊或训练处方 |
| 训练/纵向复评 | 指标与问题、目标、计划、任务和随访建立来源链；基线/复评仅在协议、版本、单位、侧别和采集条件可比时比较 | 不把单次测量差异直接宣称疗效，也不覆盖旧报告 |
| 机构运营/交付 | CRM、BPM、ERP 等仅开放审阅、迁移及权限测试通过的页面；桌面、LAN、UniApp 分别验收 | 不全量激活上游模块；不把桌面本机 `127.0.0.1` 用作手机 API 地址 |

### 3.2 拟新增的数据契约（概念设计，**本轮不改 Schema**）

- `CaptureConsent`：使用目的、对外传输目的地、供应商及版本、授权主体、取得/撤回时间、同意证据、适用的留存与删除策略。**同意不等于服务商许可**。
- `OpenCapSession`：本地 ID、租户/患者/Episode/Assessment、外部 Session ID（可为空）、来源方式、采集协议/软件版本、采集时间、设备型号、标定版本、处理状态。
- `Trial`：动作协议代码（走路/深蹲/坐站等）、重复次数、侧别、相机与采集条件、时间范围、有效性；一个 Session 多 Trial，不把不同动作混在一个 JSON 槽。
- `RawAsset`：原片、校准图/参数、`.trc/.mot/.osim`、元数据及清单；记录相对对象键、大小、SHA-256、文件真实类型、来源、版本、保留期和访问策略。`.pkl/.pickle` 只可按不透明字节归档，**绝不反序列化不可信文件**；ZIP 默认只保留原件，若解压须防路径穿越、符号链接和压缩炸弹。
- `DerivedMetric`：`name/value/unit/side/phase/time_range`、算法和模型版本、输入文件哈希、QC 状态、参考区间出处；`ClinicianReview` 单独记录确认人、意见、时间与审计。现有 `rehab_assessment_module_data.data_json` 只保留摘要/引用，不承载多机视频或所有时序数据。
- 状态建议：`planned → captured → imported → processed → qc_pass|qc_reject → reviewed → published`。所有失败可重试且幂等；QC 不通过时保留文件并显示“数据不足/需重采”，不静默补零或自动判正常。

### 3.3 横切治理与部署

后端单一鉴权，文件访问额外校验租户 + 患者授权；外部链接不直接复用可手输的 `sourceUrl` 作为服务器下载地址，以免 SSRF/越权。大文件采用受限分片/流式传输、病毒与类型检查、清单与哈希；数据库和对象存储须一致备份及恢复演练，含撤回/删除与灾难恢复边界。OpenCap 处理如需 Python/OpenSim，设计为隔离任务 Worker；桌面 Tauri 只管理本机服务，不能假设 Mac ARM 启动器自身具备 GPU 科学计算能力。外部 AI/LLM 在独立审批前继续与原片、患者资料隔离。

### 5.1 自动判读的允许范围

优先提出**待验证的量化候选**：步行方向与可用步态周期、速度/步频/步长及左右差、髋膝矢状面角度变化；深蹲的髋膝角度和次数；坐站的周期/时长。动作任务应由治疗师录制前选择并在处理时核对，不把未知动作自动识别成某种评估。指标必须附单位、侧别、时间段、采集条件、代码版本、文件哈希和 QC 标签。步态事件检出需人工抽查；低置信/遮挡/失标/出画/标定失效必须标“数据不足/需复采”，不输出伪精确的分数。力、关节负荷或肌肉激活是模型估计，应与实测量区分。SFMA/FMS/医学风险分类或治疗推荐须另行设计临床验证与监管审查，首期禁止自动落为正式结论。

### 5.2 路线选项与 Go / No-Go

| 路线 | 当前决定 | 解除阻断条件 |
| --- | --- | --- |
| A. 独立来源文件导入（首推） | **文档/格式设计 Go；真实数据接入暂缓。**用许可明确的公开或自有合成样本先验证 Session/Trial、哈希、`.mot/.trc/.osim` 兼容性 | 样本使用权、匿名化、文件安全、评估人审核；如文件来源涉及 OpenCap 云，也必须符合当时服务条款 |

## 六、下一轮“验证可行”的试点设计（本轮不执行）

**先决问题：**确认使用主体是否商业机构；能否提供两台支持的 iPhone/iPad、支架、标定板、场地和稳定网络；患者视频能否依法出境/被处理方使用；希望第一批只做步态、深蹲、坐站中的哪两项；由哪位临床负责人定义指标/参考标准。未得到商用书面许可前，不登录官方研究云进行商业试验，更不能上传真实患者片段。

1. **合法样本桌面研究：**锁定 OpenCap Core/Processing 的具体 commit 和来源许可，用公开可复用或内部充分授权的非患者样本读取目录、`.trc/.mot/.osim`、元数据及处理版本；这里只设计导入规范，不在本轮下载或运行处理链。
2. **获得授权后的现场采集试验：**两台独立 iOS 设备固定于不同视角，双方可见全身，标定板尺寸/朝向/设备/照明/距离记录成 SOP；每个步行/深蹲/坐站 Trial 记录一次同步/遮挡/失标复核。合成/志愿者须取得相应同意，不能把研究公开分享选项误读为保密协议。
3. **量化验收：**由治疗师提前规定标注和排除条件；比较人工步态事件、计时/步数/距离、必要时与压力步道或光学系统的角度/时序，按左右侧、动作速度、疾病特征、设备及场景报告失败率、绝对误差、一致性和重测差异。工程门槛：身份映射、哈希/版本追溯和越权拒绝必须完整；测量误差阈值须由临床负责人**事前**按具体指标设定，不能凭原论文总体平均误差替代。
4. **失败路径：**处理超时、断网、缺镜头、错 Session、错误附件、第三人入画、遮挡、支架移动、低质文件和复评版本不一致均必须给出重采/人工评估出口；任何失败都不能悄悄写为正常或把草稿置为已审核。

## 七、需要用户确定的四个决策

1. **用途：**内部商业门店、非营利科研，还是两者？这决定 Stanford 服务是否根本可用。
2. **数据：**是否允许可识别患者视频离开本机/香港，以及目标供应商能否访问、训练、留存？如不允许，应排除研究云并先评估合法自建。
3. **设备与首批场景：**两台 iOS 设备是否具备？先验收平地步行 + 深蹲，还是另选动作？仅有 Android 或“一台双镜头”需另立采集路线。
4. **结论权限：**首期是否同意仅做“量化提示 + 人工签核”，不对外宣称自动诊断/康复处方？

**判断等级：**对“把双机测量结果纳入现有康复评估的可审查数据链”是**有条件可行**；对“立即将商业真实患者视频接入 Stanford OpenCap 免费研究云并自动临床判读”是**明确不可行**。这些结论基于截至 2026-09-26 可核对的项目文件、官方条款/源码与论文；**没有硬件实测、账号权限验证、商用合同或临床准确率验证**。
