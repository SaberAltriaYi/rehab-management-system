# 首版范围与系统职责

## 冻结决策

| ID | S0 决策 | 原因与影响 |
| --- | --- | --- |
| D01 | 产品名称保持“运动康复评估与业务管理系统”，简称“康复管理系统”；现有正式版本标识 V1.0/1.0.0 不在 S0 改号 | 开发子服务版本不强行改成相同值，联合版本通过制品清单组合 |
| D02 | 第一交付面为单工作室内部稳定版，约3名治疗师、日均约3人次评估 | 容量与60分钟草稿时限是后续实测目标，不是已经达到的 SLA |
| D03 | 三个业务工作区：Core、运动评估/报告、HEP；Owner 独立 | 统一业务体验，不合并全部数据库或授予通用超级权限 |
| D04 | Core 继续模块化单体，现有 Java 包名/框架和 MySQL/Redis 保留 | 不借 UI 优化换底层；不引入新整套 CRM/HEP、Kubernetes 或另一套患者主档 |
| D05 | 员工日常以 Core 入口为主；运动经专门权限和单次票据进入；HEP机构操作优先用 Core 工作台 | 独立 HEP 管理/治疗师壳作为兼容入口维护，不新增重复业务，未替代验收前不删除 |
| D06 | 自动云端 AI 保持关闭；原有获授权的手工交换仍按用途和版本验证 | 不自动上传任何患者文字/图片/视频；AI只作草稿，不作数值来源或签发者 |
| D07 | CRM/会员是首版范围内的候选工作包，但必须单独通过启用门槛 | 当前制品不含 CRM 不等于当前已启用；不因源码存在就上线 |
| D08 | EMP/EPM 首版只按“员工任务/工作量与经营观察”工作定义，不视为完整 ERP | 不新增会计、供应链或薪酬结算引擎；真正独立 EPM 含义待业务复核 |
| D09 | 目录“冻结”是建立版本和处置记录，不是搬迁/删除/停止服务 | 研究分支、未知副本、旧运行环境保持原状；不能从未 Git 化推导无价值 |
| D10 | 用户要求跳过账号设置的决定继续有效 | S1 不得自动代设密码、注入身份或借其他机构患者；未完成验收如实阻塞 |

## 首版包含

1. 患者→疗程→现场 FMS/NASM-CES/SFMA 等既有表单→报告草稿/复核/归档→训练处方→复评。
2. OpenCap 授权导出资料→原件与来源核对→完整曲线/原生姿态/候选图帧→人工复核→版本化结果回传；不重做已存在的专项表单。
3. HEP：审核动作/模板、Core处方映射与下发、患者本人执行、组次/疼痛/RPE/异常、治疗师处理、可靠同步。患者侧开放须在正常身份和真机验收通过后。
4. 预约/到店签到与家庭逐组训练分开；会员服务权益、部门认领与转接按许可范围启用。
5. 生产前端、固定制品、私有存储、备份恢复、日志脱敏、安装升级和跨平台验收所需能力。

## 明确后置/不包含

- 全自动 FMS/NASM/SFMA 评分、诊断、自动开方或代签。
- 未验证的人群常模/百分位、自动云端分析、无授权的视频上传。
- 完整医院 HIS、医保/国外 RTM 结算、大型 ERP/商城/支付/IoT/BPM 业务。
- 公共健身平台、患者自由搜索全部动作/自由组课/改处方。
- 多机构商业 SaaS、Owner 公网授权运营、原生 App 商店分发的同期承诺。
- 目录/分支全量合并、删除旧数据库、数据卷或证书；新建测试账号也不是本阶段动作。

## 数据主责

| 领域 | 主责 | 契约 |
| --- | --- | --- |
| 机构/部门/员工、患者、疗程、现场评估、复评 | Core | 其他系统获取明确授权的必要子集和外部ID映射 |
| 共享客户目录、部门服务归属、会员商业权益 | Core业务域 | 临床记录不当销售备注；部门转接有接收/拒绝与审计 |
| 动作内容、训练模板和执行、疼痛/RPE/反馈/风险 | HEP | 已下发/已开始的快照不随模板追写，幂等回传 |
| 原始资料、运动派生量、图帧、分析修订 | 运动工作区 | 来源与修订绑定；仅在人工复核后提交到 Core 收件箱 |
| 正式报告归档索引 | Core | 工作区输出素材/草稿，不能使患者在两处重复签发同一报告；旧签发不被覆盖 |
| 机构许可/审批与密钥审计 | Owner | 不收病历、不与普通业务账号混成通用登录 |

S1 的最小场景以虚构成人先验收软件流程；儿童/监护人和真实资料依独立授权验证。首版覆盖人群的产品目标不等于这三类临床有效性已批准。
